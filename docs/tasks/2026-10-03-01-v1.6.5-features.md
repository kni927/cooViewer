## Part 1 — Release hygiene

### Background

The v1.6.4 release (`docs/tasks/2026-10-02-04-release-v1.6.4.md`) left three
follow-ups:

1. CI warns that `actions/checkout@v4` and `actions/cache@v4` run on the
   deprecated Node.js 20 runtime.
2. Building with the `CLAUDE.md` command, and opening `build/cooViewer.app`,
   registers build output with LaunchServices under the same bundle
   identifier and version as the installed release. At the start of release
   verification two Quick Look and two Thumbnail extensions were registered.
   This is the mechanism behind `docs/KNOWN_ISSUES.md` #15.
3. The auto mode classifier blocks creating and pushing the release tag
   (`[Production Deploy]`). **Owner decision:** the tag and the release stay
   owner actions. The agent prepares everything up to the tag and continues
   from CI monitoring after the owner pushes it.

### Goal and scope

- `.github/workflows/xcode-build-and-release.yml`: move `actions/checkout`
  and `actions/cache` to the current major versions that run on Node.js 24.
  Take the versions from the actions' official release pages or READMEs, not
  from memory, and cite them in the result. Leave
  `softprops/action-gh-release@v3` alone unless its page shows the same
  deprecation. Validate the YAML locally (`actionlint` if installed, otherwise
  a YAML parse); the real run happens at the v1.6.5 release.
- `docs/KNOWN_ISSUES.md` #15: add the v1.6.4 finding (build output is
  registered automatically), the check (`pluginkit -m -v` filtered for the
  bundle identifier, and an `lsregister -dump` filter), the cleanup
  (`lsregister -u` on build-output copies, `pluginkit -r` on their `.appex`),
  and the rule "never unregister `/Applications`".
- `docs/DECISIONS.md`: one entry, "The release tag is pushed by the owner":
  the classifier blocks it; an authorization checkbox in `TASK.md` was
  rejected as the basis for a `CLAUDE.md` exception because the agent can
  edit `TASK.md`; consequence: release tasks stop before the tag and resume
  from CI.
- Out of scope: `CLAUDE.md` (agents cannot edit or stage it). If it should
  mention the cleanup or the tag rule, put proposed text in Follow-up
  Suggestions for the owner to paste. Any other workflow change.

## Part 2 — Resolution display (#6, #7)

### Background

The page-number bar shows page number, file name and, when `ShowResolution`
is on, pixel dimensions, e.g.
`#18-19/25 (0019.jpg 1062x1500 | 0018.jpg 1062x1500)`.

1. The owner reports that the resolution is not shown when only one page is
   displayed.
2. On a spread, adding the resolution makes the page-number bar too long. The
   owner wants a third bar that shows only the resolution, next to the page
   bar and the page-number bar.

Planning-session lead (verify first): the page string is built in three
places. `-pageTextFieldString` (`Sources/BookWindowController.m`) includes the
resolution, but the ShowNumber toggle actions in
`Sources/BookWindowController_input.m` (around the two `//shownumber` cases)
build their own strings without it, so toggling page numbers drops the
resolution until the next page change. This may not explain every
single-page case.

### Goal and scope

- Reproduce problem 1 before fixing it: single-page read modes (2, 3), a
  spread book showing one page alone (cover, last page, wide page), a single
  image file, a PDF, and right after toggling ShowNumber by menu, key and
  mouse action. Record which cases fail.
- Every caller gets the page string from one formatter. No duplicated format
  strings.
- Replace the `ShowResolution` checkbox with a three-way setting
  (**owner decision**): **Off / In page number / Separate bar**.
  - Migration: if the new key is absent, read `ShowResolution`
    (YES → In page number, NO → Off). New installs default to In page number.
  - Read `ShowResolution` only for that migration.
- Separate bar, drawn by `AccessoryView` like the existing bars:
  - Shows only the dimensions; for a spread, both in the same left/right order
    as the page-number bar, e.g. `1062x1500 | 1062x1500`.
  - Same font, colors, background and auto-hide behavior as the page-number
    bar; next to it without overlapping either existing bar, in every
    page-bar position setting.
  - Hidden when the setting is not Separate bar, or when no book is open.
- Localize new UI strings (en, ja).
- Out of scope: a new key/mouse action for the resolution bar (follow-up if
  useful); any change to image drawing in `CustomImageView`.

### Notes

- Image quality rule (`CLAUDE.md`): bars are overlays in `AccessoryView`. Do
  not touch the decode → `drawInRect:` path. State the resampling-step count
  before and after (unchanged).
- Pixel dimensions come from `NSImageRep` (`docs/KNOWN_ISSUES.md` #6).
- Spread left/right mapping depends on `readMode` (`docs/KNOWN_ISSUES.md`
  #3): test all four modes.
- Nib changes must keep outlets in sync (`docs/KNOWN_ISSUES.md` #2); launch
  after editing to catch KVC crashes.

## Part 3 — Window entry points (#1, #3, #4, #5)

### Background

v1.6.3 added the Finder Open With entry **cooViewer (New Window)** through a
bundled helper app (`NewWindowHelper/`). v1.6.4 moved the Finder routing rule
into one method, `-[AppController openFilesPreferringFrontWindow:entry:]`,
used after launch and by the launch drain, with `WindowRouting` logging.

The owner wants:

1. An icon for the helper's Open With entry. Planning-session finding
   (verify): the helper target uses `Resources/Info.plist` but neither
   compiles `Assets.xcassets` nor sets `ASSETCATALOG_COMPILER_APPICON_NAME`.
2. **⇧ Shift**-open (**owner decision**): holding ⇧ while opening from Finder
   with the ordinary **cooViewer** entry (double-click, Open With, ⌘↓) opens
   in a new window. (⌘ was rejected: Finder's keyboard Open holds ⌘ by
   definition.) The helper stays.
3. Drag and drop of files onto a book window opens them there, with the same
   rules as a Finder double-click (**owner decision**).
4. **File ▸ New Window** (⌘N) creates an empty book window.

### Goal and scope

**Shared routing, one place.** Generalize the existing method so it takes
the target controller explicitly — for example
`-openFiles:preferringWindow:entry:` — with the front controller for Finder,
the drop target for D&D, and nil to force new windows for ⇧. Keep
`-openFilesPreferringFrontWindow:entry:` only as a thin wrapper if that reads
better. No second copy of the gate. Add `WindowRouting` lines for the new
entry points (e.g. `finder-openFiles+shift`, `drop`, `menu-new-window`).

**Helper icon.** Add the asset catalog (or only `AppIcon`) to the helper's
Resources phase and set `ASSETCATALOG_COMPILER_APPICON_NAME = AppIcon` for all
helper configurations. Verify from the built bundle (`CFBundleIconName` /
`CFBundleIconFile`, `Assets.car`). The Finder Open With icon is checked at
release verification.

**Shift-open.**
- In `-application:openFiles:`, read `+[NSEvent modifierFlags]` when the
  request arrives. With ⇧ held, every file in the call goes to
  `-openBookInNewWindow:` (dedup and empty-window reuse still apply), the same
  result as ⌥⌘O. Without ⇧, unchanged.
- During launch, read ⇧ at receipt, not at drain time, and tag the queued
  request (as helper requests already are) so the drain sends it to
  `-openBookInNewWindow:`.
- On device, confirm that ⇧-double-click still opens the file and Finder
  sends only the expected file (⇧-click extends the selection), that ⇧ does
  not alter the Open With submenu, and that ⇧⌘↓ works. If ⇧ proves unusable,
  stop and report; do not pick another modifier.

**Drag and drop onto a book window** — same rules as a Finder double-click,
with the drop target in place of the front window:
- Accept file URLs that File ▸ Open accepts; copy cursor only for those.
- Dedup first: a file already open in any window brings that window forward.
- The first remaining file goes into the drop target: it replaces the book if
  the target has one, or fills the target if it is empty — not when the
  target is loading (`-isBookLoadInFlight`), waiting for a password
  (`-isWaitingForUserInput`), or awaiting a restored book; then it goes to
  `-openBookInNewWindow:`.
- Every further file goes to `-openBookInNewWindow:`. ⇧ does not change drops.
- Register for drags on the book window's content view (or
  `CustomImageView`) without changing mouse handling:
  `docs/KNOWN_ISSUES.md` #5 (right-click / case 59) must keep working.

**File ▸ New Window.**
- Menu item **New Window** (⌘N) above Open… in the File menu (en, ja).
- Creates a bookless book window, sized like a genuine new window in
  `-openBookInNewWindow:`.
- When the front window is empty, an ordinary Finder open fills **that**
  window, not another empty one. Check what `-emptyWindowController` returns
  with several empty windows and make the front empty window win.
- Must follow MW-8 rules for bookless windows (not restored as a phantom, no
  quit-on-last-close side effects). Confirm from source.
- Check for collisions with configurable key actions
  (`BookWindowController_input.m`).

Out of scope: removing or renaming the helper; default (no-modifier) Finder
behavior; Dock icon drops beyond `-application:openFiles:`; drags from inside
cooViewer; the v1.6.4 follow-up about the front window when the app is
inactive at drain time.

Image quality rule: none of Part 3 touches decode → draw. State that in the
result.
