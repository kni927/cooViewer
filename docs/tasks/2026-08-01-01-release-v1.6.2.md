## Draft release notes (for owner review — do not tag with these unreviewed)

Draft, user-facing framing (adjust wording, this is a starting point):

```markdown
## v1.6.2

- New book windows now open at the same size as the window they were
  opened from (via "Open in New Window…" or Finder), instead of always
  resetting to the default size.
- Opening a file from Finder while a cooViewer window is already open
  now loads it into that window, instead of opening a new one each
  time. "Open in New Window…" still always opens a new window.
```

The spread-diff tool and methodology docs are internal/dev-facing —
owner's call on whether to mention them in release notes at all;
default assumption is no, unless the owner wants them included.

## Release procedure

Follow `CLAUDE.md`'s "Releasing" section exactly:

1. Confirm the draft release notes above (or the owner's edited
   version) and the version number `v1.6.2` with the owner explicitly.
   **Do not tag without this confirmation** — pushing the tag is the
   irreversible publication step.
2. Push the `v1.6.2` tag. This triggers
   `.github/workflows/xcode-build-and-release.yml`: builds Deployment,
   signs bottom-up, notarizes via `xcrun notarytool`, staples, creates
   the GitHub Release with `cooViewer-v1.6.2.zip` attached.
3. Watch the CI run to completion. If notarization fails, **stop and
   report** — do not work around Gatekeeper (no ad-hoc signing, no
   clearing quarantine, no disabling checks).
4. **Verify the release artifact** per CLAUDE.md's "Verifying the
   release artifact" procedure — this is a third, distinct case from
   the on-device verification procedures used during development:
   - `brew uninstall cooviewer`, then install the released version
     from the tap (before step 5, so the tap still needs updating —
     see next step; sequence per CLAUDE.md may require updating the
     tap formula first for this install step to resolve v1.6.2 at all,
     confirm the actual required order and note it in the report if it
     differs from this task's ordering).
   - Confirm it launches and is Gatekeeper-clean without `xattr -cr`.
   - QuickLook/Thumbnail checks per steps 3a-5 of the On-Device
     Verification Procedure, reading `/Applications` as the bundle
     under test.
5. Update the Homebrew tap formula (`kni927/tap`, `cooviewer`):
   version, URL, sha256. Confirm a fresh install resolves to v1.6.2
   and launches.
6. Spot-check the two shipped behaviors on the real released build
   (not just the dev builds already verified during implementation):
   - Open a window, resize it, "Open in New Window…" — new window
     matches the size.
   - With a window open, Finder-open a different file — loads into the
     existing window instead of opening a new one.

### A safety incident during real-build spot-checking, caught and corrected

Doing the item-6 spot-checks against the **real, live `/Applications`
install** meant working in the user's actual profile
(`jp.coo.cooViewer`), which had a real book open and restored from the
user's last session. Acting too quickly after `open
/Applications/cooViewer.app` (before the restored book had finished
its background load — a real manga file, larger and slower to decode
than this project's tiny test fixtures), a ⌥⌘O test found
`-openBookInNewWindow:`'s existing `emptyWindowController` check still
seeing the front window as bookless (`hasBookOpen` not yet `YES`) and
reused it instead of creating a new window — **not a code regression**
(neither `-openBookInNewWindow:` nor ⌥⌘O's own action were touched by
this release; this is a pre-existing timing window in already-shipped
code, triggered here only because a real, larger file was still
loading when the test fired), but it did replace the user's real book
in its window.

**No data was lost.** `defaults read jp.coo.cooViewer RecentItems`
confirmed the book's title, alias, and exact page (`page = 70`,
0-indexed → displayed as "P71") were preserved before the replace ever
happened (the existing "remember previous book on replace" mechanism,
unrelated to this release, already guarantees this). Restored it
immediately via File ▸ Recent Books ▸ the exact title, confirmed back
at the identical window frame (`142,31, 1609×1035`) — matching before
and after exactly. Re-ran both spot-checks afterward with a longer
settle delay before scripting, confirming clean results with the
manga window never touched a second time (see below). This is recorded
here in full rather than glossed over, since it is the kind of incident
CLAUDE.md's Executing-actions-with-care guidance exists for, even
though the net effect on the user was zero (a few seconds of a menu
click to restore, nothing unrecoverable).

### Follow-up Suggestions

- The `emptyWindowController` race (a restored book's `hasBookOpen`
  can still read `NO` for a brief window while a large file finishes
  its background load, letting a subsequent open incorrectly treat the
  window as reusable) predates this release and is not part of its
  scope, but is a real, reproducible timing issue worth its own
  investigation task — especially now that both ⌥⌘O and Finder-open
  rely on `-openBookInNewWindow:`/`emptyWindowController`'s notion of
  "empty" being accurate.
- Consider documenting, alongside the existing On-Device Verification
  Procedure, that real-build spot-checks against the live
  `/Applications` install (as opposed to an isolated test copy) should
  wait for any restored book to fully finish loading before scripting
  further actions — this incident is the concrete case for it.
