# MW-7 follow-ups: quit-on-last-close, Window menu, openFiles, lookahead join

## Goal

Clear the four items MW-7 explicitly deferred, before starting MW-8.

## Background

From the MW-7 completion report (`docs/tasks/2026-07-29-11-mw7-open-in-new-window.md`):

- Step-0 decision 4 (quit when the last window closes) was deliberately
  **not** implemented in MW-7. Reason recorded in `docs/DECISIONS.md`:
  `-openPage:last:` closes the just-fronted window when the very first open
  of a session fails, so naively setting
  `applicationShouldTerminateAfterLastWindowClosed:` to YES would quit the
  app the moment someone opens a single corrupt file at launch.
- No Window menu listing open windows yet — with MW-7 making multiple
  windows a normal state, there's currently no menu-based way to switch
  between them (only clicking on-screen or Cmd+`~` if that's even wired).
- `application:openFiles:` (Finder "Open With" / drag-onto-dock-icon) isn't
  handled — unclear currently what happens when a file is opened that way
  post-MW-7; needs to route through the same `AppController` window
  registry / dedup-by-resolved-path logic MW-7 built for
  `-openInNewWindow:`.
- The lookahead thread (background page pre-loading) is never explicitly
  joined. Not urgent single-window, but worth checking whether it's now a
  per-window or per-app thread, and whether window close / app quit can
  race it.

## Scope

1. **Decision 4 — quit on last window closed, safely.** Implement
   `applicationShouldTerminateAfterLastWindowClosed:` returning YES, but
   first close the gap that made MW-7 defer it: distinguish "user closed
   the last remaining window" from "`-openPage:last:` closed the
   just-fronted window because the first open of the session failed."
   Candidate approaches to evaluate against the actual code (pick one,
   don't assume): only enable the quit-on-close path once at least one
   window has successfully shown a book in the session; or have
   `-openPage:last:`'s failure-path close route through a different,
   non-counted teardown than a genuine user-initiated window close. Verify
   the exact failure scenario from the MW-7 report no longer quits the app.
2. **Window menu.** Add a standard Window menu (or extend an existing one)
   listing open windows by title, checkmarking the frontmost, selecting an
   item brings that window forward. Should read from the `windowControllers`
   registry `AppController` already maintains (MW-7) rather than duplicating
   window tracking.
3. **`application:openFiles:`.** Implement/fix so Finder "Open With" and
   drag-onto-dock-icon opens route through the same registry and
   dedup-by-resolved-book-path logic as `-openInNewWindow:` — reuse rather
   than reimplement the resolution (`+resolvedBookPath:`) and dedup MW-7
   already added.
4. **Lookahead thread join.** Establish current behavior first (per-window
   vs per-app, current lifecycle), then add an explicit join at the
   appropriate teardown point(s) — likely window close given MW-7 made
   windows a per-book unit, but confirm before assuming.

## Out of scope

- MW-8 itself (this task exists specifically to precede it).
- Any other item not in the four above, even if related code is touched
  incidentally.

- Spread capture SHA-256 unchanged (render path untouched by this task).
- `NSZombieEnabled` + `leaks` pass, particularly around item 1 (repeated

  - Open several books in several windows, close them one at a time down

  - Window menu reflects open windows live as they're opened/closed/

  - Open a file via Finder "Open With" while the app is already running

  - Drag a file onto the dock icon while the app isn't running — launches

## Implementation Result

**Status:** Completed

### Changes

Three commits on `main`, `c61d63e`..`7d47628`, plus this docs commit.
**Item 2 required no code** — see below. The commit order was chosen after
reading the code: the four items are independent, so they are committed
smallest-blast-radius first (item 4, item 3, item 1), and each intermediate
tree was built to confirm the split leaves no unbuildable commit.

- **Item 2 — Window menu: already correct, nothing written.** Established
  before touching anything: `Resources/Base.lproj/MainMenu.xib`'s Window
  menu carries `systemMenu="window"`, so AppKit maintains the window list
  itself. Verified on device with three windows open — the menu listed
  `bookA`/`bookB`/`bookC` by title, check-marked the front one, brought a
  window forward on selection, followed a window's title when its book was
  switched, and excluded the panels (`NSPanel` is excluded by default).
  Building a second list from `windowControllers` would have duplicated
  AppKit's own tracking, which is the opposite of what the task's guidance
  was protecting against. Recorded in `docs/DECISIONS.md`.
- **Item 4 — lookahead join** (`c61d63e`). Behaviour established first: the
  lookahead is **per-window** (instance methods over one window's
  `imageMutableArray`/`cacheArray`/`imageLoader`, detached from
  `-lockedImageDisplay`). `threadCount` looks like a join counter but is
  incremented *after* `lock` is taken, so `-windowWillClose:`'s
  `[lock lock]`/`[lock unlock]` pair waited only for threads already inside
  the body — a thread detached a moment earlier and still blocked on the
  same lock went straight through. New `pendingLookaheadCount` is
  incremented **before** the detach; `-joinLookaheadThreads` sets
  `threadStop`, drains the count, and keeps the lock round-trip as a final
  barrier. It runs at **both** teardown points, not only the one the task
  named: `-openPage:last:`'s replacement of the previous book destroys the
  same state. The wait is bounded at 2 s because `-loadImage:` can reach an
  archive read whose progress path is driven from the main thread; a
  timeout degrades to the pre-existing behaviour, which is safe because
  `+detachNewThreadSelector:toTarget:` retains the target.
- **Item 3 — `application:openFiles:`** (`e169b26`). Finder "Open With",
  Dock drags and the launch document event now go through the MW-7 registry
  and its de-duplication instead of being forwarded to the front window;
  one window per file for a multiple selection. `-application:openFile:` is
  removed from both classes, since AppKit prefers the plural callback and a
  second, unreachable path is worse than none. `-emptyWindowController` was
  added because "reuse the front window if it is empty" is not
  deterministic inside a single pass over a file list —
  `-frontController` only changes when AppKit sends
  `-windowDidBecomeMain:`. File ▸ Open still replaces (decision 3).
- **Item 1 — quit on last window closed** (`7d47628`).
  `-applicationShouldTerminateAfterLastWindowClosed:` returns YES once
  `didShowBook` is set, i.e. once some window has actually shown a book.
  Of the two approaches the task offered, this is the first; the second
  (a separate non-counted teardown for the failure close) was rejected
  because AppKit decides when to ask the delegate, so the session flag
  would have had to exist anyway.
  **Finding, and a correction to MW-7's premise:** the failure path is
  narrower than MW-7 assumed. A corrupt or empty book does *not* reach it
  — `COImageLoader` appends a placeholder page whenever a load yields no
  items, so `-openPage:last:`'s `itemCount < 1` guard is dead code and a
  garbage `.cbz` opens as a one-page book. The reachable trigger is
  `mode = -1`: a cancelled archive read or a cancelled password prompt.
  That is recorded as `docs/KNOWN_ISSUES.md` #30, and the password-prompt
  case is what was used to reproduce the hazard.
  Also required by this item: `-closeAuxiliaryPanels` now runs on **every**
  window close, not only on retirement. MW-7 restricted it deliberately;
  decision 4 makes that impossible, because a panel left on screen is a
  visible window and AppKit would never ask the delegate at all.

### Verification

- **Build:** clean `Deployment` build. **310 warnings**, and the normalised
  (file + message) diff against the MW-7 baseline — re-measured at
  `4a379c6` in this session, also **310** — is **empty**. *Measurement
  caveat worth recording:* one run of the same clean build reported 309,
  because a single `NSControlKeyMask` deprecation in
  `ThumbnailController.m` (a file this task does not touch) was missing
  from one of the two architectures' output. A re-run gave 310 and an empty
  diff. `xcodebuild`'s warning output is not perfectly reproducible; treat a
  one-line delta in an untouched file as noise and re-run before chasing it.
  Each of the three intermediate commit trees was built separately.
- **Render path:** the pre-MW-7 build (`063d458`) and this build, captured
  minutes apart at a fixed window frame from an identically restored
  profile, are **byte-identical (SHA-256 `e80f3f2b…`)**. *Note for future
  tasks:* the absolute hash is **not** stable across sessions — comparing
  this run against MW-7's recorded `b16c9892…` showed a difference, and a
  pixel diff located it in the **bottom 42 rows only** (window corner
  anti-aliasing, ±2/255), with all 1558 rows of page content identical. The
  capture includes window chrome, so it must be compared within a session
  against a freshly built baseline, not against a hash recorded earlier.
- **On device**, test build only (`build/cooViewer.app`); `/Applications`
  never touched, no `lsregister`/`pluginkit`. Defaults exported before and
  restored after — final diff is **zero delta across all 81 top-level
  keys**.
  - **The MW-7 hazard, reproduced then shown fixed:** opening
    `tests/engine/out/enc_aes.zip` as the first action of a session and
    cancelling the password prompt closes the window — and the app **stays
    running**. File ▸ Open then reopens into the surviving controller from
    a zero-window state.
  - **Quit on last close:** one window with a book → ⌘W → app quits. Three
    windows → closing the first two leaves it running, closing the third
    quits. With the Filter panel open on the **last** window, ⌘W still
    quits (the panel-blocks-termination case item 1 had to fix).
  - **Finder opens:** app not running, two files at once → two cascaded
    windows (73,30) and (102,59). Already running, reopening an open book →
    its window comes forward, no new window. Already running, a new book →
    a third window at (131,88). File ▸ Open on the front window still
    replaced its book with three windows open.
  - **Lookahead join:** twelve rapid page turns followed immediately by ⌘W,
    and by an immediate File ▸ Open of another book — no hang, no crash, no
    zombie, under `NSZombieEnabled`.
  - **`NSZombieEnabled`** over the whole sequence (presence confirmed with
    `ps eww`): **no zombie message**, empty log apart from the expected
    "password required" line.
  - **`leaks`** on a zombie-free build before and after opening + closing a
    second window with page turns in flight: 310 → 338 blocks, **zero
    cooViewer per-window objects leaked** in either snapshot (the delta is
    the same system/XPC noise plus the pre-existing leaks recorded as #29).
- **Not performed:** Instruments; multi-display; Apple Remote;
  QuickLook/Thumbnail (untouched); an actual Finder drag onto the Dock icon
  — driven through `open -a`, which delivers the same Apple Event, rather

### Remaining Issues

None for the four items. One pre-existing finding was recorded rather than

### Follow-up Suggestions

- **#30 wants a UX decision.** Whoever takes it should separate "this book
  has no readable pages" from "this page failed to decode", and decide
  whether a failed open should tell the user rather than silently closing
  the window.
- **`-[FilterPanelController deleteFilter:]`** still drops a KVO-observed
  `CIFilter` (#28), and the Alias Manager helpers still leak a few
  `CFString`s per open (#29). Both predate MW-7.
- **`-validateMenuItem:`'s 24 `[[self window] isVisible]` tests** are still
  the "is a book open" proxy MW-6 item 4 replaced elsewhere.
- **Window tabbing.** With multiple windows the system Window menu now
  offers Merge All Windows / Show Next Tab. Tabbed book windows have never
  been exercised and may interact with the per-window panels and the
  cascade; worth a look before MW-9's regression pass.
- KNOWN_ISSUES #24 (All Bookmark browser has no UI entry path) remains
  open. MW-6 suggested revisiting it when a Window menu appeared; the menu
  turned out to be AppKit's, so there is still no natural home for it.
