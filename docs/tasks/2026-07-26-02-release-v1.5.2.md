# TASK: Release v1.5.2 (cvbdl QuickLook support, notarized)

## Scope

Full release: version bump, code signing verification, notarization,
GitHub Release, and Homebrew tap update. This covers both the encrypted-ZIP
work (v1.5.1, tagged but never released) and the cvbdl QuickLook support
added since. The release supersedes v1.5.1 as a version marker — v1.5.2 is
the first version actually distributed since v1.5.0.

Prerequisite (already done by the project owner, not part of this task):
a `notarytool` keychain profile named `cooViewer-notary` exists.

## Step 1: Version bump

1. Update `MARKETING_VERSION` / `CURRENT_PROJECT_VERSION` to `1.5.2` across
   all targets and configurations, as done for v1.5.1.
2. Confirm `docs/DEV_LOG.md` entries for both the encrypted-ZIP milestone
   and the cvbdl milestone reference this release; add "(v1.5.2)" where a
   version number is now appropriate. Do not duplicate entries.
3. Commit.

## Step 2: Build and sign

1. Clean `build/` per the existing convention.
2. Build the Deployment configuration with a Developer ID Application
   signing identity (not the ad-hoc/unsigned identity used for local dev
   builds). Report the exact identity used and confirm it matches a
   Developer ID Application certificate:
   `security find-identity -v -p codesigning`.
3. Verify signing: `codesign --verify --deep --strict --verbose=2
   build/cooViewer.app`, and confirm the two extensions are signed as part
   of the same identity/team.
4. Zip the app for notarization and distribution:
   `ditto -c -k --keepParent build/cooViewer.app cooViewer-1.5.2.zip`.

## Step 3: Notarize

1. Submit: `xcrun notarytool submit cooViewer-1.5.2.zip
   --keychain-profile "cooViewer-notary" --wait`.
2. Report the submission ID and status. If it is `Invalid` or `Rejected`,
   retrieve and report the full log
   (`xcrun notarytool log <submission-id> --keychain-profile
   "cooViewer-notary"`) and stop — do not proceed to stapling on a failed
   submission.
3. On success (`Accepted`), staple the ticket:
   `xcrun stapler staple build/cooViewer.app`.
4. Verify: `xcrun stapler validate build/cooViewer.app` and
   `spctl -a -vv build/cooViewer.app` (expect
   "source=Notarized Developer ID").
5. Re-zip the stapled app for distribution:
   `ditto -c -k --keepParent build/cooViewer.app cooViewer-1.5.2.zip`.

## Step 4: On-device verification of the notarized build

Follow the QuickLook/Thumbnail procedure in `CLAUDE.md`, including step 3a
(confirm which bundle Finder actually resolves). This is the first chance
to verify the cvbdl QuickLook support on real Finder behaviour — the
implementation task (2026-07-25-17) could not complete this because the
Homebrew-installed `/Applications` copy took priority.

1. Before this step only, uninstall the Homebrew-managed copy:
   `brew uninstall cooviewer` (confirm the exact formula name first;
   report it).
2. Install `cooViewer-1.5.2.zip` (the notarized, stapled build) to
   `/Applications` for this verification pass — this is the actual release
   artifact, not a throwaway test copy, so installing it to `/Applications`
   is appropriate here (unlike the disposable `~/Applications` builds used
   during development).
3. Verify: `.cvbdl` fixture shows a correct thumbnail and Quick Look
   preview; encrypted ZIP (traditional + AES) prompts, opens, and
   re-prompts on wrong password as before; ordinary CBZ/CBR unaffected.
4. Do not reinstall Homebrew's version yet — Step 6 replaces it via the
   tap update, which will reinstall the released version.

## Step 5: GitHub Release

1. Tag `v1.5.2` (annotated), pointing at the version-bump commit from
   Step 1. Push commit and tag.
2. Create a GitHub Release from the tag, with release notes covering:
   - restored password-protected ZIP support (traditional + AES-256,
     including Japanese passwords) — the headline feature, originally
     dropped in v1.4.0
   - cvbdl bundle QuickLook/Thumbnail support
   - note that encrypted RAR remains unsupported (reference
     `docs/DECISIONS.md`)
3. Attach `cooViewer-1.5.2.zip` (the notarized, stapled build) as a release
   asset.
4. Report the release URL.

## Step 6: Homebrew tap update

1. Locate the tap repository/formula (report where it lives).
2. Update the formula's version, URL (pointing at the new release asset),
   and sha256 checksum (`shasum -a 256 cooViewer-1.5.2.zip`).
3. Verify the formula installs cleanly:
   `brew install --build-from-source <formula>` or equivalent, per however
   the tap currently distributes it (source build vs. prebuilt bottle —
   report which).
4. Commit and push the tap update.
5. Confirm `brew upgrade cooviewer` (or a fresh `brew install`) now
   resolves to 1.5.2 and that the installed copy launches.

## Notes

- Step 4's `brew uninstall` is the one exception to the general rule of
  not touching `/Applications`; it exists to make room for the actual

## Implementation Result

**Status:** Completed — v1.5.2 fully released (notarized, GitHub Release
published, Homebrew tap updated and verified), with two deviations from
the task's literal wording, both surfaced and confirmed before acting.

### Deviation 1: CI pipeline used for build/sign/notarize/release instead of local manual steps

Before touching anything, found `.github/workflows/xcode-build-and-release.yml` —
a working, previously-successful (v1.4.0 through v1.5.1, all
`github-actions[bot]`-authored) pipeline that on a `v*` tag push builds,
signs with the Developer ID identity, notarizes via the App Store Connect
API key, staples, and creates the GitHub Release with the correctly-named
asset — i.e. it already automates Steps 2, 3, and most of 5 as literally
described. This directly contradicts the task's framing (manual local
codesign + local `notarytool` keychain-profile submission + manual
`gh release create`). **Asked the user which path to use rather than
silently picking one**, given the real-world stakes (Apple notarization
submission, public release); the user chose the CI path. Steps 2/3/5.1/5.3
were therefore done by pushing the tag and letting CI run, not by local
`codesign`/`notarytool`/`ditto`/`gh release create` commands. Step 5.2
(curated release notes) and Step 4 (on-device verification against the
real artifact) still required manual work and were done as described
below.

### Deviation 2: Homebrew tap distributes via Cask, not Formula/bottle

Step 6 assumes a Formula (`brew install --build-from-source <formula> or
... prebuilt bottle`). The actual tap (`kni927/homebrew-tap`,
`Casks/cooviewer.rb`) is a **Cask** — a thin wrapper that just points at
the GitHub Release zip URL and unpacks the `.app` into `/Applications`;
there is no formula, no source build, no bottle. Updated and verified it
as a Cask (`brew install --cask cooviewer`), which is the actual
mechanism in use; noted here rather than forcing the task's Formula-shaped
wording onto a Cask.
